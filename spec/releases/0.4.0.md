# Dashhaus 0.4.0

Status: written in its release PR, at the commit whose files [0.4.0.sha256](0.4.0.sha256) records. It
shipped when [v0.4.0](https://github.com/Krystosterone/dashhaus/releases/tag/v0.4.0) exists.

## Release page

Orb and Field now each install on their own from the Home Assistant Marketplace, under their own names, and each one
lists itself in **Settings → Dashboards → Add dashboard**. The Dashhaus download is gone: this release adds no file to
it, so move to Orb or Field with the steps below. On npm, `@dashhaus/bundle` and `@dashhaus/dashboard` are gone too:
each skin's package ships its own file, and the dashboard framework is now `@dashhaus/core/lovelace`.

### Upgrading

From the Dashhaus download in the Marketplace:

1. Install Orb or Field (or both) from its page:
   [krystosterone.github.io/dashhaus/orb/](https://krystosterone.github.io/dashhaus/orb/) or
   [krystosterone.github.io/dashhaus/field/](https://krystosterone.github.io/dashhaus/field/).
2. Reload the browser tab.
3. Go to **Settings → Dashboards → Add dashboard** and pick the skin.
4. Delete the Dashhaus dashboard, any **Home (Orb)** or **Home (Field)** dashboard the old setup card made, and the
   setup card itself.
5. Remove the Dashhaus download.

A dashboard you wrote yourself on Orb's or Field's card (`custom:dashhaus-orb`, `custom:dashhaus-field`) keeps
working once that skin is installed.

From npm, deploying from the command line:

1. Replace `@dashhaus/bundle` with the skins you deploy:
   `npm uninstall @dashhaus/bundle && npm install @dashhaus/orb@^0.4.0 @dashhaus/deploy@^0.4.0` (add
   `@dashhaus/field@^0.4.0` for Field).
2. In `dashboard.config.mjs`, replace `bundle: fileURLToPath(bundlePath)` with `files: [resourceFile]`, importing
   `resourceFile` from `@dashhaus/orb/resource` or `@dashhaus/field/resource`. A dashboard can now name a skin's
   strategy instead of a card, `strategy: { type: "custom:orb-dashboard" }`, and follow the skin as it updates.
3. Deploy, then delete the old `/local/dashhaus/dashhaus.js` under **Settings → Dashboards → Resources**, since it
   defines the same cards.

If you call `@dashhaus/deploy` from code, `resolveBundle` is now `resolveFiles`, which returns one target per file, and
`deploy()` returns `{ resources, dashboards }` instead of `{ version, resource, dashboards }`.

If you build a skin, drop `@dashhaus/dashboard` from its `package.json`, move `@dashhaus/core` to `^0.4.0`, and change
each import: `@dashhaus/dashboard` becomes `@dashhaus/core/lovelace`, and `@dashhaus/dashboard/skin`, `/card`,
`/schema`, `/layout` and `/conformance` become `@dashhaus/core/lovelace/skin`, `/card`, `/schema`, `/layout` and
`/conformance`.

## What changed since 0.3.0

### Breaking changes

- @dashhaus/bundle is gone: each skin's package now ships its own file. To deploy from the command line, install @dashhaus/orb or @dashhaus/field (or both) with @dashhaus/deploy instead of @dashhaus/bundle, and in dashboard.config.mjs replace bundle: fileURLToPath(bundlePath) with files: [resourceFile], importing resourceFile from @dashhaus/orb/resource or @dashhaus/field/resource. Your dashboards keep working. After the first deploy, delete the old /local/dashhaus/dashhaus.js under Settings → Dashboards → Resources, since it defines the same cards.
- @dashhaus/dashboard is now part of @dashhaus/core, under its ./lovelace subpaths. A skin drops @dashhaus/dashboard from its package.json and changes each import: @dashhaus/dashboard becomes @dashhaus/core/lovelace, and @dashhaus/dashboard/skin, /card, /schema, /layout and /conformance become @dashhaus/core/lovelace/skin, /card, /schema, /layout and /conformance. Nothing else changes, and an app that only uses core's hooks loads none of it.
- @dashhaus/deploy takes a list of files and two kinds of dashboard. A dashboard can name a skin's strategy, strategy: { type: "custom:orb-dashboard" }, and follow the skin as it updates, or give its card config directly instead of a card() factory. bundle: is gone: name the file in files: instead. If you call the package from code: resolveBundle is now resolveFiles, which returns one target per file, and deploy() returns { resources, dashboards } instead of { version, resource, dashboards }.
- The Dashhaus download from the Marketplace, with Orb and Field in one dashboard, is gone: Orb and Field now each install on their own, and this release adds no file to the Dashhaus download. To move: install Orb or Field from its page (krystosterone.github.io/dashhaus/orb/ or /field/), reload the tab, and add its dashboard under Settings → Dashboards → Add dashboard. Then delete the Dashhaus dashboard, any Home (Orb) or Home (Field) dashboard the old setup card made and the setup card itself, and remove the Dashhaus download. A dashboard you wrote on Orb's or Field's card (custom:dashhaus-orb, custom:dashhaus-field) keeps working once that skin is installed.

### New

- Orb and Field each have their own page on the site and their own Marketplace install, Krystosterone/orb-dashboard and Krystosterone/field-dashboard, whose releases carry the file inside the skin's npm package once its provenance checks out. Add dashboard describes each in its own words.
- Orb and Field each list themselves in Home Assistant's Add dashboard under their own name, and in the card picker as Orb and Field. A skin made with create-dashhaus-skin does too: defineSkinStrategy from @dashhaus/core/lovelace/skin gives it a dashboard strategy of its own.

### Fixed

- A card's config errors and a stopped dashboard no longer say Dashhaus: they read "The card's config has 2 problems" and "The dashboard stopped".
- Freshly scaffolded skins install successfully with the updated Vite and React plugin versions.
- New standalone skins install their Vite 8 development dependencies without a React plugin peer conflict.

Internal changes, left out: 1.

## API changes since 0.3.0

Read from the packed type declarations (`npm run release:api`). A removed entry or export, or a changed
declaration, is breaking until a person says otherwise.

- **Changed** `generatedDashboards` in `@dashhaus/deploy/config`
- **Changed** `DeployDashboard` in `@dashhaus/deploy/config`
- **Changed** `DeployConfig` in `@dashhaus/deploy/config`
- **Changed** `CardFootprint` in `@dashhaus/orb`
- **Changed** `CardProps` in `@dashhaus/orb`
- **Changed** `SheetProps` in `@dashhaus/orb`
- **Changed** `TileProps` in `@dashhaus/orb`
- **Changed** `AutoInput` in `@dashhaus/orb/lovelace/auto`
- **Changed** `AutoState` in `@dashhaus/orb/lovelace/auto`
- Added entry `@dashhaus/core/lovelace`
- Added entry `@dashhaus/core/lovelace/skin`
- Added entry `@dashhaus/core/lovelace/card`
- Added entry `@dashhaus/core/lovelace/schema`
- Added entry `@dashhaus/core/lovelace/layout`
- Added entry `@dashhaus/core/lovelace/conformance`
- Added entry `@dashhaus/orb/resource`
- Added entry `@dashhaus/field/resource`
- Added `DeployCardFactory` to `@dashhaus/deploy/config`
- Added `DeployCardConfig` to `@dashhaus/deploy/config`
- Added `DeployStrategy` to `@dashhaus/deploy/config`
- Added `DeployDashboardBase` to `@dashhaus/deploy/config`
- Added `DeployCardDashboard` to `@dashhaus/deploy/config`
- Added `DeployStrategyDashboard` to `@dashhaus/deploy/config`
- Added `ORB_STRATEGY` to `@dashhaus/orb/lovelace/card`
- Added `FIELD_STRATEGY` to `@dashhaus/field/lovelace/card`

Every changed declaration above is owned by a breaking note:

- `generatedDashboards`, `DeployDashboard` and `DeployConfig` in `@dashhaus/deploy/config` are the note that
  `@dashhaus/deploy` takes a list of files and two kinds of dashboard (`bundle` became `files`, and a dashboard is now
  a card dashboard or a strategy dashboard), with the `@dashhaus/bundle` note for `bundle:`.
- `CardFootprint`, `CardProps`, `SheetProps` and `TileProps` in `@dashhaus/orb`, and `AutoInput` and `AutoState` in
  `@dashhaus/orb/lovelace/auto`, are the note that `@dashhaus/dashboard` is now part of `@dashhaus/core`: 0.3.0
  re-exported them from `@dashhaus/dashboard/card` and `/layout`, which the comparison reads as `any`, and 0.4.0
  re-exports the same declarations, unchanged, from `@dashhaus/core/lovelace/card` and `/layout`.

Run 2026-11-06 by an agent (Claude Code) for the operator, who approved it and logged the browser in,
on Home Assistant `2026.11.0`, at the candidate commit `6dc2db5`, on the `0.4.0` tarballs `npm run release` packed
there. All five match [0.4.0.sha256](0.4.0.sha256), and each journey ran in a fresh app installing only those tarballs.

One difference from spec/release.md's commands, and one thing on the instance:

- The author journey installed the scaffold the way CI's `verify/dx/author.js` does,
  `npx create-dashhaus-skin my-skin --tarballs <release>` then `npm install` inside it. The spec's pins (`vite@5.4.19`,
  `@vitejs/plugin-react@4.3.4`) predate the scaffold's Vite 8: it asks for `vite ^8.3.6` and `@vitejs/plugin-react
  ^6.1.2`, and got 8.3.6 and 6.2.1, with React 19.3.1.
- The instance also had the 0.3.0 Dashhaus download from the Marketplace installed
  (`/local/community/dashhaus/dashhaus.js?v=1441397762-v0.3.0`), as an upgrading user does until Upgrading's step 5,
  and two older dashboards from this repository's own deploy (`dashhaus-orb`, `dashhaus-field`), left alone. Both
  0.3.0's file and 0.4.0's define a card only when it isn't defined yet, so whichever runs first wins: here the
  registered `dashhaus-orb` and `dashhaus-field` classes are the source in `orb-dashboard.js` and

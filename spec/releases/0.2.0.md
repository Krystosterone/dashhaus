# Dashhaus 0.2.0

Status: release candidate · 2026-10-31 · not tagged, not published, no registry smoke

Seven public packages share the fixed version `0.2.0`. The two clean-room journeys pass from freshly packed
tarballs. The tree cleanup is done, the rebuilt tarballs contain no child name or absolute home path, and the old
repository was deleted and recreated so the rewritten history is the only remote history. The live Home Assistant
smoke has run. Publishing is still blocked by one failed live-smoke observation (the scaffolded skin has no details
surface) and branch protection; see [Publish gate](#publish-gate). The owner chose to keep `Krystosterone`,
`Krystian Czesak` and `krystianczesak@gmail.com` public, so those remain in links and commit metadata by design.

## What changed since 0.1.0

`0.1.0` was an internal candidate and never reached the registry; there is no published package to upgrade from.
Everything below is new to a registry consumer. Relative to the `0.1.0` candidate, which carried core, dashboard and
deploy only:

- **The two skins are packages.** `@dashhaus/orb` and `@dashhaus/field` expose `.`, `./lovelace/card`,
  `./styles/tokens.css` and `./storybook`; Orb also exposes `./lovelace/auto`. Their code is unchanged in behaviour,
  but a consumer now imports the package subpaths instead of reaching into this repository.
- **`@dashhaus/bundle` is new.** It ships the prebuilt `dist/dashhaus.js`, registers `custom:dashhaus-orb` and
  `custom:dashhaus-field`, and exports `bundlePath` as a file URL. A deploy-only app installs it plus
  `@dashhaus/deploy` and builds nothing; the repository deploys the same file it ships.
- **`create-dashhaus-skin` is new.** It writes a standalone skin with one control card, one reading card, the real
  core hooks, a YAML reader, the element, a conformance test, a Vite build that emits one file, and a
  `dashboard.config.mjs`. No Storybook, no workspace and no repository path. The build is named for the skin
  (`dist/dashhaus-<skin>.js`) and deploys under its own `/local/dashhaus-<skin>/` resource, so a scaffolded skin can
  live on the same instance as the prebuilt `@dashhaus/bundle`.
- **The consumer guide and package READMEs are written.** `spec/build-a-skin.md` is the standalone author journey;
  each of the seven packages has a non-empty README in its tarball.
- **The public contract is named.** `@dashhaus/dashboard/skin` is the frozen skin-author surface,
  `@dashhaus/dashboard/card` the shared card frame, `./schema` and `./layout` are pure, `./conformance` is the
  generic card preset, and `@dashhaus/deploy/config` is the pure config surface. `spec/contract.md` records what a
  third-party skin may rely on.
- **Both consumer journeys are executable.** `verify/dx/user.mjs` and `verify/dx/author.mjs` install only packed
  tarballs into temporary apps, deploy into an in-memory Home Assistant, and never touch the workspace. The `dx` CI
  lane runs them after `release:pack` and `verify:packages`; the required `check` job includes that lane.
- **Release tooling follows the fixed version.** `release:version` now rewrites the scaffolder template's internal
  ranges as well as every manifest, and `verify:packages` reads the packed template back. A scaffolded skin
  therefore installs `^0.2.0`, not a stale `^0.1.0`.
- **Version:** all seven public manifests and their internal ranges move from `0.1.0` to `0.2.0`.

## Breaking changes a consumer must act on

`0.1.0` was never published, so no registry user has a migration. If you built against the `0.1.0` tarballs:

1. **Reinstall all `@dashhaus` packages together.** The internal ranges are now `^0.2.0`; mixing a `0.1.0` tarball
   with a `0.2.0` one does not dedupe. `@dashhaus/deploy`, core and dashboard must come from the same line.
2. **Skins are imported by package, not by repository path.** Replace relative imports into a clone with
   `@dashhaus/orb` or `@dashhaus/field` and their declared subpaths. `./lovelace/card` registers the Lovelace
   element; `./styles/tokens.css` ships the stylesheet; Orb's `./lovelace/auto` is its generated layout.
3. **Deploy-only apps install two packages.** `@dashhaus/bundle` and `@dashhaus/deploy`; no React, core or dashboard.
   `bundlePath` is a file URL, so pass it through `fileURLToPath` in `dashboard.config.mjs`. The CLI reads
   `dashboard.config.mjs`, not `dashhaus.config.mjs`, unless `--config` names another file.
4. **Apps that build a skin bundle install `home-assistant-js-websocket`.** It remains an optional peer, but the
   element base reaches `@dashhaus/core/websocket`, so Vite cannot bundle the card without it. React 18 is required;
   the deploy CLI needs Node 22 or newer.
5. **Import the frozen surfaces, not internals.** A skin imports `@dashhaus/dashboard/skin`; the config surface is
   `@dashhaus/deploy/config`; the YAML reader and layout are `@dashhaus/dashboard/schema` and
   `@dashhaus/dashboard/layout`. There is no `@dashhaus/dashboard/cli` or `/vite` package entry in this line.
6. **If you copied an older scaffold, update its ranges and its bundle name.** A skin scaffolded from a pre-`0.2.0`
   template pins `^0.1.0`; set its `@dashhaus/core`, `@dashhaus/dashboard` and `@dashhaus/deploy` ranges to `^0.2.0`.
   The old template also emitted `dist/dashhaus.js`, which collides with the prebuilt bundle; rename the Vite output
   and the config's `bundle` to a skin-specific file such as `dist/dashhaus-my-skin.js`.

## Publish gate

1. **The remote history is clean by recreation.** The old private repository was deleted and recreated on
   2026-11-01. The new repository carries the rewritten candidate `5a6cce8`; `main` is that candidate plus this docs
   record, while `dx/guarantee` remains at the candidate. It has 223 rewritten commits, no `ci/gate-speedups` branch,
   and clean child-name/home-path scans on a fresh clone. The seven old merged PRs and the old Actions history
   were lost with the deletion; their metadata is backed up at `/tmp/dashhaus-repo-backup/`. The old local clone was
   reset to the recreated remote and garbage-collected on 2026-11-01.
2. **The live smoke has run, with one failed observation.** Observations 1–5 pass; observation 6 fails because the
   scaffolded skin has no details surface. Fix the scaffold or explicitly amend the acceptance criterion before
   publishing.
3. **Branch protection is not enabled.** The protection API answers 403 on the private repository; `check` and
   `storybook` are the intended required contexts, and `check` now includes the `dx` lane. The operator chose to leave
   this blocker; enabling it needs GitHub Pro or a public repository.
4. **Publishing is manual and last.** There is no publish job in CI. Publish the tarballs in the order above, then
   rerun both journeys from the registry, not the tarballs.

# Home Assistant integration

The dashboard remains a React/TypeScript component library. The normalized entity models (`LightEntity`, `ClimateEntity`, …) live in `packages/core/src/entities/`, free of any UI, so more than one skin can sit on them; a skin's cards take those models and callback actions as props. Home Assistant wire data is owned by `packages/core/src/ha/`, whose mappers and actions import only from `packages/core/src/entities/`.

## Data flow

```text
Home Assistant auth + connection
  -> injected transport / official websocket adapter
     -> shared entity store (raw snapshots + connection status)
        -> pure domain mapper + capability gate
           -> useHa<Kind>() hook: { entity, history, actions }
              -> any skin; in orb, the Ha*Tile container -> Tile/Card props
              (or the hook as a headless component: <HaLight entityId>{(light) => …}</HaLight>)
```

The store is the source for current state. A successful service call means Home Assistant accepted the command; it is not proof that the entity reached the requested state. The next entity snapshot is the readback boundary.

To surface a rejected action, read `useHaSnapshot()` or pass `onActionError` to an individual `Ha*Tile`; `useActionStatus()` from `@dashhaus/core/lovelace/skin` gives a recovery row its words, Retry and Dismiss. Every skin's Lovelace page (Orb's `ConfigDashboard`, Field's `FieldDashboard`, a generated skin's dashboard and the scaffold's page) reads the shared store once through it and shows one page-level recovery row with the affected entity, Retry when repeating the call is safe, and Dismiss. The row floats at the bottom of the view, so it is in sight wherever the failed control was, and it never moves a card. Wrong alarm codes stay in the keypad, where the specific recovery already exists. The raw entity snapshot remains authoritative for readback.

The store routes action service calls through `callService` and background reads through `query` (forecasts, calendar events) or `callApi` (generic websocket commands such as `history/history_during_period`), the last two never mutating action ordering or `lastActionError`. A rejection is classified as `transport_unknown` when the connection changed during the call or the library reports `ERR_CONNECTION_LOST` (code `3`), otherwise `service_failed`. The codes, their categories and the retry rule are in [core.md](core.md#error-metadata).

`packages/core/src/websocket.ts` adapts an official `home-assistant-js-websocket` connection. Entities come from the library's `subscribeEntities` collection, which decodes the compressed `subscribe_entities` stream and resubscribes on every reconnect; the library reconnects with backoff. The adapter forwards `ready`, `disconnected` and `reconnect-error` (invalid auth, after which the library stops retrying) as `connected`, `disconnected` and `error`.

## Auth and transport security

Auth is a host concern: `@dashhaus/core` has no auth provider, auth hook, login UI, token storage or token refresh. See [core.md](core.md) for the frozen core surface and the full boundary.

## Contract rules

- Preserve raw `state`, `attributes`, `last_changed`, and `last_updated` before mapping.
- Treat every snapshot as the update, not the state word: attributes can change without the state string changing (`brightness`, a cover's position, `hvac_action`, a weather reading), so a mapper and the cards that select it redraw from the whole entity, never only when `state` differs.
- Keep `unknown`, `unavailable`, and a missing entity distinct from `off`. Lights and covers keep `unknown` as a state of their own, since Home Assistant drives them in it (a light group before its first state, an optimistic MQTT or RF light before its first command, an RF blind or a garage door with no sensor on an assumed state); every other domain maps it to unavailable.
- Derive light capabilities from `supported_color_modes`; do not infer support from a stale `brightness` attribute alone.
- Convert Home Assistant brightness (`0..255`) to the card's percent contract (`1..100`). If a capable light has not reported brightness, reports a non-finite/out-of-range value, or its raw state is `unknown`/`unavailable`, keep normalized brightness and Kelvin readings absent while retaining capability metadata; never send or display a fabricated measured value. Home Assistant reports no brightness while a light is off, so an off or unknown light still draws its brightness control, with no level; only a lit light with no reading falls back to on/off.
- Treat `last_changed` as a state-transition timestamp, not as proof of last reachability. `lastSeen` is populated only from explicit adapter metadata.
- Accept timestamps only when their ISO date/time components are valid; reject nonexistent timezone-less local times during DST gaps and do not let JavaScript date normalization turn impossible values into plausible display times. Display them relative to the tile's minute clock: the time for today, weekday and time within the last week, the date before that (`formatHaTime`), the time on the dashboard's hour cycle: every `useHa<Name>` hook reads it (`useHourCycle`) and hands it to its mapper as `hourCycle`, so no mapper formats with the browser locale's clock behind the dashboard's back.
- Reject non-finite brightness/Kelvin inputs and Kelvin values outside the entity's reported range before sending a service payload.
- Climate modes/actions, current/target temperatures, ranges, limits, presets, and fans are mapped only from their raw attributes. A climate entity names no unit, so its unit is the card's `unit`, else Home Assistant's own unit system (`get_config`, read once per connection), else °C. Missing current or target readings stay absent, and stale measured values are suppressed while the raw entity is unknown or unavailable; documented Home Assistant defaults are used only for control metadata needed by the normalized card.
- Climate range actions order `target_temp_low <= target_temp_high`, validate both values against the reported bounds, and use `climate.turn_on`/`climate.turn_off` rather than inventing a prior HVAC mode.
- Sensor mappers parse numeric `sensor.*` states for the supported temperature, humidity, and battery device classes; when `device_class` is absent, a recognized temperature unit may provide the temperature fallback, but an explicit other class wins over a contradictory unit. Companion humidity/battery entities are optional, percentage values outside `0..100` are omitted, blank/invalid numeric states are omitted, and unknown/unavailable primary entities suppress normalized readings rather than exposing stale attributes.
- Weather mappers accept the documented Home Assistant condition set, suppress current readings while the weather state is `unknown` or `unavailable`, reject invalid humidity/UV/wind/AQI values, and never infer `isDay` from a missing or unavailable `sun.sun` companion. Only an explicit AQI companion with `device_class: "aqi"`, a declared `aqiScale="US"`, and a `0..500` value is mapped into the repository's US-AQI model; without the scale assertion, AQI remains absent.
- Weather forecasts are a separate `weather.get_forecasts` query product. The integration requests `hourly` and `daily` scopes with a target and response flag through `store.query`, which stays out of action ordering and `lastActionError`, reads each scope once per hour (keeping the previous hour's forecast up while the next loads), deduplicates in-flight requests by store/generation/entity/scope/hour across StrictMode effect replay, requires a valid forecast timestamp before accepting any record (even when an explicit hour/day field is present), rejects contradictory explicit hourly fields instead of letting a convenient fallback override the timestamp, uses local-calendar hours so DST does not create 23/25-hour rollover values, validates condition/temperature fields, rejects inverted daily high/low bounds, omits incomplete daily records, ignores late results across reconnects with generation checks, and reports each rejected request via `onForecastError` while retaining a successful result from the other scope; no forecast value becomes a current reading.
- Keep domain action payload construction in `packages/core/src/ha/actions/`, not in cards or Storybook stories. Each module runs its services through `serviceRunner()` (`packages/core/src/ha/actions/run.ts`), which sanitizes rejections and refuses actions on an unavailable entity (raw `unavailable`, or missing; a light or cover in `unknown` still acts); an entity whose state is `on`/`off` reads today through `onOffHistoryFromHass`.
- Cover mappers gate position, stop, and tilt on the entity's `supported_features` bits, keep `unknown` as its own drivable state rather than closed or unavailable (with its stale position and tilt dropped), and never send the card's presentation fallback position back as measured state.
- Toggle integration reads the domain (`input_boolean` or `switch`) from the entity id, so `ToggleEntity` needs no field for it; the card's timed-on sheet feature stays a host timer hook because neither domain has a native duration service.
- Alarm mappers default `codeArmRequired` to true, map unrecognized states including `unknown` to unavailable, and take delay/open-sensor metadata from host options rather than inventing it. Alarm actions resolve false only for a recognized wrong code (the sanitized `invalid_code` translation-key scalar); any other rejection, including a bare service-validation scalar, means the call did not go through, and codes are never logged or persisted.
- When a compact home card hides its control (`footprint="compact" showControl={false}`), preserve the normalized details interaction: the value row remains keyboard and pointer activatable and opens the existing details sheet.
- Keep optimistic interaction state separate from the current-state mapper. Histories and registry metadata are their own read-only slices: pure per-domain parsers over `history/history_during_period` rows plus a registry lookup, fetched through `store.callApi`, never a current reading and never action state.

### History slice

`packages/core/src/ha/useHaHistory.ts` reads the local day through `history/history_during_period` (`entity_ids`, local midnight to now, `include_start_time_state`, `significant_changes_only: false` so attribute-only changes such as brightness, position, `hvac_action` and weather temperature are included). The response is an object keyed by entity id holding compressed rows `{ s, a, lu, lc? }` with epoch-second times; `packages/core/src/ha/fixtures/history_during_period.json` follows that shape. (Earlier revisions called `recorder/history_during_period`, which does not exist; a fixture for a wire contract comes from the server's source or a capture, never from the parser it tests.) After the read, every live change to the requested entities extends the day, so the strip stays current without polling; the read repeats for every new connection generation and at local midnight. Failures resolve to no history; `loadHistory={false}` or a host-supplied `history` prop replaces the read.

`packages/core/src/ha/history.ts` parses rows into records (a row's time is `lu`, falling back to `lc`; rows without attributes carry the previous row's forward) and walks them per domain into the existing history models. The latest record from before midnight is the state carried into hour 0; records after `now` are ignored; the hour axis is local-calendar (DST days still yield 24 samples); hours before the first record read `unavailable` for state domains and `null` for readings; minute totals count full past hours plus the current minute. Climate derives `activity` from the day's dominant `hvac_action`; sensor composes temperature plus an optional humidity entity; weather reads the `temperature` attribute because its state is a condition; cover uses position when the entity reports it.

### Registry slice

`packages/core/src/ha/registry.ts` reads `config/entity_registry/list_for_display` (`{ entities: [{ ei, ai?, di? }] }`), `config/device_registry/list`, `config/area_registry/list` and, best-effort, `config/floor_registry/list` once per connection generation, shared by every tile. `useHaRegistry()` returns the typed lists and entity-registry display map; `useHaAreas()` returns each area with its entity IDs; `useHaArea(entityId)` returns the area name for one entity. The pure `areaMembership` resolves an entity's area: its own area wins, otherwise it inherits its device's area, which is how most entities get one. Areas with no name, and entities whose area is unknown, are left out. Every read resolves to unavailable when the transport lacks generic commands, and the floor read alone does not take the other three down. Tiles use the result as the `area` fallback after their explicit prop.

### Energy preferences

`packages/core/src/ha/energy.ts` reads Home Assistant's energy preferences, what the person set up on the Energy dashboard, with `energy/get_prefs` (`ENERGY_PREFS`): `readEnergyPrefs(send)` takes a `sendMessagePromise`-shaped function and resolves to the raw `EnergyPrefs` (`energy_sources`, each with its `type` and its statistic ids, `stat_energy_from`, `stat_energy_to` and `stat_rate`, flat or in a grid's older `flow_from`, `flow_to` and `power` lists), or to nothing: Home Assistant's `not_found` ("No prefs", never set up), any other refusal or error, and an answer of the wrong shape all give none, and a source that isn't an object with a `type` is dropped. It is pure, so the layout's types name it. The Lovelace element reads it lazily, only for an automatic layout, once per frontend connection (`LovelaceDashboardElement.energyPrefs`, spec/contract.md), and `energySensors` in `@dashhaus/core/lovelace/layout` picks the house's electricity sensors from it (spec/cards.md → Numeric). The demo transports answer it with `DEMO_ENERGY_PREFS` (a grid with `sensor.grid_power` and `sensor.house_energy`); the fake Home Assistant answers `not_found` unless it is given preferences.

## Development checks

In development only, every `useHa<Name>` hook checks its entity ID once: a malformed ID or one from the wrong domain warns once in the console with the hook's name and expected domain. Production builds are silent, a warning never throws, and a missing entity is not warned about — a dashboard may legitimately render one before its entity loads. The behavior is pinned by `packages/core/src/ha/dev.test.ts`.
